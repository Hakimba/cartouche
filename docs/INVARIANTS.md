# Invariants

Guarantees every change must keep. Each id is part of the name of the test (or tests) enforcing it.
Weakening one is a design decision to discuss first, never a side effect of a change.

| Id | Area | Invariant | Why |
|---|---|---|---|
| INV-E0-01 | Launch | Templates can never grant URI permissions: `--grant-*` and any `-f` value with a grant bit are rejected, and a `LaunchSpec` can only be built by resolving a template (its constructor is internal). | Player definitions are third-party data. |
| INV-E0-02 | Launch | Only the game's own URI is ever granted, exactly when the launch depends on it; no other content URI is handed where Android grants access with the intent (the data URI, `--eu` extras). | A template must not reach other files in a granted folder. |
| INV-E0-03 | Launch | Placeholder values are inserted verbatim in every kind of value, including string arrays. | A file name with quotes, commas or `-n …` must not change the launch. |
| INV-E0-04 | Launch | Parsing and resolving templates is total: a template or a typed error, never an exception. | Bad data is reported, not a crash. |
| INV-E0-05 | Launch | Single- and double-quoted tokens tokenize back to themselves. | The tokenizer never loses or alters characters. |
| INV-E0-06 | Launch | A template needing `{file.path}` never launches a file without a filesystem path. | Otherwise the emulator starts with an empty ROM argument. |
| INV-E0-07 | Catalog | Every definition file shipped in `app/data/platforms` parses with no rejection. | Updating bundled data must not silently lose emulators. |
| INV-E0-08 | Catalog | A broken or duplicate player is rejected alone, a broken or duplicate platform, or one without a Cartouche profile, whole, and every rejection is reported. | Nothing disappears silently. |
| INV-E0-09 | Catalog | Hidden files (`.x`, `._x`) are never offered to a player, whatever the patterns say. | They are not games. |
| INV-E0-10 | Catalog | Catalog parsing and file matching are total. | As INV-E0-04, for definition files and names. |
| INV-E0-11 | Storage | Only documents of the external storage provider map to a filesystem path; the mapping is total. | `{file.path}` must never point to a guessed location. |
| INV-E0-12 | Android | Whatever the template, a launch intent grants read access to the game URI when it hands it, and to nothing else; it never grants write, persistable or prefix access. | The emulator can open the game; nobody can write to ROM folders. |
| INV-E0-13 | Android | Launches always start a new task and keep the template's activity switches. | Templates are written for `am start`. |
| INV-E0-14 | Android | Only read access to a picked folder is kept. | Cartouche never writes to ROM folders. |
| INV-E0-15 | Android | Every folder pick is answered exactly once: by its result, by the failure to open the picker, or as cancelled by a newer pick. | A screen awaiting a pick never hangs or gets two answers. |
| INV-E0-16 | Android | Everything the plugin sends to Godot is a value its JNI bridge converts: text, booleans, numbers, Dictionaries, lists of Dictionaries as `Object[]` and lists of texts as `String[]`. | Any other array, and a String inside an `Object[]`, reaches GDScript as an opaque object. |
| INV-E1-01 | Library | Every file a scan lists ends up in exactly one place: a disc of one game, or the ignored files. Copies and other formats of a game stay separate games. | Nothing disappears or merges silently. |
| INV-E1-02 | Library | A scan does not depend on the order the folder lists its files in. | The same folder always gives the same library. |
| INV-E1-03 | Library | Reading a game name is total, never gives a blank title, and reading a title again gives the same title. | Any file name is shown as something readable. |
| INV-E1-04 | Library | By its name (when what it holds names no game, INV-E11-01), a file is only identified as a reference disc of the same title and edition (not a demo or beta for a retail file) that nothing in its name contradicts (region, languages, version, disc): as that very disc when its name is written exactly as it, or when a single one matches its name exactly (disc number included), otherwise only by the serials all possible discs share, and not at all if they share none. A game so identified shows the regions, languages and version its file name states. Reference names identify as themselves. | A wrong serial or name is worse than none. |
| INV-E1-05 | Library | A stored library reads back identical. | Restarting the app never changes the library. |
| INV-E1-06 | Library | A rescan keeps what was chosen for games still there, drops games whose files are gone, and changes no other platform. | Rescanning is always safe. |
| INV-E1-07 | Library | Only a file that a player of the platform accepts becomes a game; hidden files and BIOS files never do. | Emulator data and system files are not games. |
| INV-E1-08 | Library | An unreadable library file is set aside, never overwritten. | A bug or a bad write does not destroy the user's library. |
| INV-E1-09 | Library | A scan lists every file of its folder and, with sub-folders on, of its sub-folders, each once, even when the provider lists a folder in two places. A sub-folder it does not look into (hidden, emulator data, 8 or more levels down, or unreadable) is listed with the reason, and never hides anything else. | Nothing disappears silently or shows twice, and one bad folder does not spoil a scan. |
| INV-E1-10 | Library | Without sub-folders, a scan lists the platform's folder only. When that folder cannot be listed, the scan fails. | The choice is honoured, and a removed SD card does not empty the library. |
| INV-E1-11 | Library | A scan ends whatever the documents provider answers, including a folder listed inside itself. | A faulty provider cannot hang the app. |
| INV-E1-12 | Android | Whatever rows a documents provider returns, or however it fails (including a listing cut short), listing a folder gives all its entries or a typed failure, never a crash or a partial listing. | Documents providers are third-party code. |
| INV-E1-13 | Library | The stored library, and the library sent to Godot, grow with games, with files a player opens and with skipped folders (all bounded by the 10,000 entries of a scan), never with hidden or unsupported files: those are only counted, with their first names. | A folder of emulator data or downloads cannot slow the app down. |
| INV-E1-14 | Library | A scan fails past 10,000 entries (files and folders), naming the folder that listed the most, and changes nothing. Cartouche reads at most one entry more from a documents provider, though the provider itself still lists each folder whole. | The worst scan takes seconds, and a partial scan never drops games. |
| INV-E1-15 | Library | A sub-folder named like emulator data (`app/data/scan/data_folders.json`, any case) is reported and never listed. The list holds none of the usual names of game folders (`roms`, `games`, platform ids). | Emulators keep tens of thousands of files next to the games. |
| INV-E2-01 | Shelves | Every platform of the catalog that has games has one shelf, in catalog order (unless the user put the consoles in an order, INV-E7-08), holding exactly its games in title order whatever the order of the library. Each shelf starts on the remembered game, else the one that followed it, else the first; the carousel starts on the remembered platform, else the first. | Coming back always lands somewhere sensible, even after games are gone. |
| INV-E2-02 | Carousel | A game is never shown twice at once, and never hidden within reach: a stopped row shows the selected game in the middle and its consecutive neighbours; a shelf that fits on screen (4 games at most, see `WHOLE_SHELF`) is shown whole, in order, without wrapping around. A game appears or leaves only where it cannot be seen, and never jumps from one end to the other. | A shelf of two or three games must not look like more, or less. |
| INV-E2-03 | Carousel | Each step moves exactly one game along the endless row, whatever the speed: n steps one way then n the other come back to the same game. | No game is ever skipped. |
| INV-E2-04 | Carousel | A held direction repeats faster and faster, never more often than every 48 ms (20 steps a second at 60 fps), and releasing it stops the steps at once. | Fast, but the user always stops where they let go. |
| INV-E2-05 | Shelves | A stored selection reads back the same; an unreadable selection file only means starting from the first game; a rescan keeps the selected game while it is there. | Restarting or rescanning does not lose the user's place. |
| INV-E2-06 | Carousel | Every media of the platforms has a model, and every model loads with a `Label` mesh the carousel can draw on. | Replacing a model is data only, and cannot break a shelf. |
| INV-E2.5-01 | Carousel | Without the Android plugin (editor, desktop), the catalog is the plugin's for the shipped definitions, and the demo library a fresh one with nothing selected, both exactly as the plugin sends them. The Kotlin test is `INV-E2_5-01`, as test names cannot hold a dot. | Models and materials are tuned on a computer, on the shelves the device shows. |
| INV-E2.5-02 | Models | A disc built from any dimensions it accepts is closed, every face turned outwards; it fills exactly its size and nothing comes into its hole; the label covers the top exactly between its radii, a label image covering the whole face upright, and the mirror the bottom from its inner radius to its outer one, marked recorded only between the data radii. | A disc has no gap or stray face at any size, and a scanned label lands where it is printed. |
| INV-E2.5-03 | Models | Carried by INV-E10-07 since every cartridge is its own medium's shape: each, built from any dimensions it accepts, is closed, every face turned outwards, and fills exactly its size, its label on its face, the image upright. | The shell has no hole or fold, whatever its notches, bevel and label. |
| INV-E2.5-04 | Models | Impossible dimensions are refused with the reasons and build nothing; every shipped model is built from dimensions that fit, each of its parts with faces. | A wrong number in a model's data is reported, never drawn as a broken model. |
| INV-E2.5-05 | Carousel | Every game shows a label: its image when there is one, else its title, in the ink (dark or white) further from the label's colour, at least 0.43 apart in luminance; on made-up artwork, white ink with an outline. | A game without artwork can still be told apart. |
| INV-E2.5-06 | Carousel | On a stopped row, only the selected game is posed: the games beside it stand as the layout places them, and the pose keeps within its tilt, turn and sway. | The pose never breaks INV-E2-02's layout. |
| INV-E2.5-07 | Carousel | The right stick turns the selected game any way, up to its back; let go, the game stays exactly as it was left, and the games beside it do not move; once another game is selected, the one turned turns back to the front as it leaves, and the one arriving turns from its front. | A game can be looked at from every side, its back included, without holding the stick. |
| INV-E3-01 | Launch | Checking whether a game can launch starts no activity and stops no process, whatever it finds. | The check runs before the insertion plays, and must not end a game left running. |
| INV-E3-02 | Launch | A launch fails exactly as its check did, and goes ahead exactly when its check did; it stops a lingering emulator only when it goes ahead and the definition asks to. | The insertion only plays for a game that starts. |
| INV-E3-03 | Launch | A game whose file is gone, or whose storage cannot be read, never launches; when its emulator is there (or Android picks one), it fails as `game_missing`. Every launch failure reaches the carousel with its own code. | A removed SD card gives a clear message, not an emulator error. |
| INV-E3-04 | Carousel | Whatever a launch comes to (refused at the check or at the start, started then back, back or gone before the start is answered, never left for the emulator, a check or a start never answered), the carousel shows again as it was: the same game selected and where the row places it, each control as present as before it (the consoles screen's name stays hidden on the games screen), no spindle and no black. A started game keeps the screen all black until the user comes back, or for 5 s at most while the launch waits for an answer or for Android to leave for the emulator. A refused launch shows its message; a game that cannot start plays no insertion. | Coming back is always clean, and a failure never leaves the screen black. |
| INV-E3-05 | Carousel | From A until the carousel shows again, no input acts, not even one begun before A (a held direction, the stick, Select): the selection and the shelf do not change, and no second launch starts. | Buttons pressed during the insertion or the game cannot launch another game. |
| INV-E3-06 | Android | There is never more than one curtain, and every one comes down: after its time (10 s at most, longer times are refused), as soon as Cartouche is back, or at once if the start it covers fails; without the permission, or with a time of zero, none is raised. Lowering it when Cartouche is back is the plugin's, checked on a device. | A black screen can never stay over the emulator. |
| INV-E3-07 | Carousel | An insertion starts where the game stood, never moves faster than its steps take it, and ends seated on the spindle, facing the drive; the drive spins the game from its seating only, never backwards, and only with a spindle; the black grows from nothing to the whole screen once the game is seated. | The motion reads as putting a disc in a drive, whatever its timings. |
| INV-E3-08 | Carousel | Every medium has an insertion lasting at most 1.8 s. | The check and the start keep 0.2 s of the 2 s from A to the emulator. |
| INV-E4-01 | Art | A game only ever gets scans of its own disc: those of the one game its title names in the art extract (fan-made images are not in it), closest to its regions first (its own region, its group's umbrella, the rest of its group, the world, then NTSC-U, PAL, NTSC-J), equally close ones a zone's own name (North America, Europe, Japan) before its other countries, then in the extract's order; then those its platform's serial source names after its own serials. Never a box cover. | A label is always the right game's real disc, as close as possible to the user's copy. |
| INV-E4-02 | Art | A title finds its game whatever its case, accents, punctuation and spaces: by an alternate name written `<title> (<one of the game's countries>)` first, then by the game's name before its alternate names, words kept apart before joined (a name of no Latin letter, such as a Japanese one, is found by its romanised alternates); several games found are told apart as INV-E11-02 says. | A near miss in a name still finds the art. |
| INV-E4-03 | Art | Whatever the network, the servers and the app do (stops, starts, scans, stalls, retries), a game is looked for by one request at a time, its image downloaded once at most, never looked for again once found unless scraping again is asked (debug builds), and a resumed run asks for exactly what is left. | Scraping is resumable and never downloads twice. |
| INV-E4-04 | Art | Only whole images are taken for stored ones: an interrupted or failed write leaves no image. | A cut during a download never shows a broken label. |
| INV-E4-05 | Art | A network or server failure never makes a game give up: it is tried again, after a delay that doubles from 30 s to 15 min, or as soon as the network is back; only a game none of the sources has is remembered as without art, until the sources change. | Being offline or over a quota costs nothing: the art comes later. |
| INV-E4-06 | Art | Stored images are found without the network, whatever it does, under the file names every version gave them, and looking for the others never waits for it. | The carousel shows what it has at once, offline too; renamed, images (the user's own pictures too) would be taken for those of games gone, and deleted. |
| INV-E4-07 | Carousel | A scan that arrives replaces the title drawn on its game in view, and nothing else: the other games keep their labels, every game its place, the selection stays. | Labels appear as they come, without moving the carousel. |
| INV-E5-01 | Carousel | The right stick turns the selected console on the consoles screen only: never while going in or out, on the games screen, or during a launch; going in turns it back to the front. | The console is looked at where it is chosen, and stands as its animation has it everywhere else. |
| INV-E5-02 | Carousel | The right stick turns the selected game on the games screen only (INV-E2.5-07 there); a game turned then launched still leaves from where it stood and ends on the spindle. | A disc is looked at where it is chosen, and goes in whatever way it was turned. |
| INV-E5-03 | Carousel | A launch animation made from steps reaches each step exactly and holds it until the next leaves; between two steps each value follows the step's curve (the cubic ones exactly, the rebound within a tenth of the way beyond); before its start and after its end it holds its first and last step; its moments (consoles, games, launch, seated, black) fall where its steps have them. Put into its console, the disc leaves from where it stood. | What was tuned in the animation's steps is what plays, and nothing jumps. |
| INV-E5-04 | Carousel | Going into a console then back out leaves the consoles screen exactly as it was (same console, standing as its animation starts), and the games screen finds the game it was left on. | Going in and out is free to try. |
| INV-E5-05 | Carousel | While the console opens or closes, nothing pressed acts: neither console nor game changes, no launch starts, Select does not open the device check. | A press during the animation cannot go somewhere else than where it leads. |
| INV-E5-06 | Carousel | The carousel opens on the consoles screen, on the remembered console, still; back from a game, it is on the games screen as it was left (INV-E3-04). | Opening Cartouche starts from the consoles, and a game ends where it started. |
| INV-E5-07 | Models | A console built from any dimensions it accepts is closed part by part, every face turned outwards; the lid's opening goes through its top down to the well, the lid fills it but for its gap, turning about its back edge so that its front rises; a seated disc's centre is over the well's centre, at its seat height, its axis up. Impossible dimensions are refused with the rules they break and build nothing. | The console has no hole or stray face at any size, and a disc lands where the lid closes over it. |
| INV-E5-08 | Launch | Every console with a launch animation takes a game from the games screen to the whole screen black: in 2.4 s at most with the placeholder (INV-E10-03), in the time its own steps take otherwise. | A launch always ends on the black, as fast as the PS2 unless a console's own animation is designed longer. |
| INV-E6-01 | Screens | On each screen in front of the carousel where something is chosen, after any moves, exactly one control has the focus, visible and on that screen; back from the form adding a console, the focus is on the button that opened it. | The controller always shows where it acts, and never gets lost. |
| INV-E6-02 | Controls | Confirming and going back follow the device's own A and B, as its settings send them; the button style chosen only changes how buttons are drawn, never an action. | A validates and B goes back as in every other app on the device. |
| INV-E6-03 | Library | Removing a platform leaves nothing of it in the library (choices, games, files set aside, counts), in the selection, in the stored art (images and absences), in what its game files told (`files/facts`) or in the folder access kept, unless another platform uses that folder; the other platforms are as they were, and the game files are not touched. An image whose game is no longer in the library goes at the latest when art is next looked for, and is never looked for again; while the library cannot be read, no image and no folder access goes. | Removing a console takes away everything Cartouche kept of it, and only that. |
| INV-E6-07 | Screens | The form adding a console chooses nothing in advance and never offers a platform already set up; once one more console is added, the consoles screen comes back on it. | Adding a console never replaces one, and shows the one just added. |
| INV-E6-05 | Settings | The first launch shows only while no controller was set up and no platform was: once the controller is set up, or on an app already set up (updated from a build without settings), it never shows again. | Setting the app up happens once. |
| INV-E6-06 | Library | The games counted for a folder before a platform is added are the games its scan finds once it is added, whatever the folder and choices; counting saves nothing. | The number shown before adding is the number the user gets. |
| INV-E7-01 | Library | Which image a game's label shows, once chosen, is kept through saving, reading back and any rescan that keeps the game's file; it goes with the game (its file gone, its platform removed). Games whose label is automatic store nothing for it. | A label chosen is there after a restart and a rescan, and costs nothing to games left as they are. |
| INV-E7-02 | Carousel | Whatever is pressed during a game's or a console's properties, and when, they always settle on one whole screen (for a console: the consoles screen with it back in the row, its properties with the focus on its name or on "Change place", or its name's keyboard, or the ring putting the consoles in order, INV-E7-09); for a game: the games screen with the disc back in the row, the properties with the disc staged and the focus on its label or its name, its images with the disc staged higher and the focus on a card (a region's, or the user's own picture's), a picture of the user's own being framed, the disc showing it and no focus, or the keyboard of its name with the focus on a key. No press counts while the plugin answers. | The properties never stop half-way, and the controller always shows where it acts. |
| INV-E7-03 | Art | A game's images are every image of its sources, each named by its region and its source (« Europe · ScreenScraper », « Europe · LaunchBox »), the first of each region (regions named alike, `USA` and `North America`, are one) and source, in the order they are tried (INV-E11-07); ScreenScraper's are left out while it has no key or is not open, and a texture it answered it has none of is too. A chosen label keeps its region and its source, and that image is looked for first, among exactly the same images as before; a choice stored before images had a source is LaunchBox's, all the chooser offered then. (Changed in E11 v4 with the user's agreement, 2026-10-18: one image per region and source, from both sources, instead of one scan per region.) | The images offered are the game's own, and a chosen one is what its label shows again if the art must be fetched anew. |
| INV-E7-04 | Art | A game whose label shows a picture of the user's own is never looked for by scraping, whatever its sources have: no download replaces it. Scraping again (debug builds) leaves it as it is, and a label of a region the user chose too. | A picture of one's own stays on its label through restarts, rescans and new art extracts. |
| INV-E7-05 | Art | Any framing of a picture of the user's own, whatever its values and the picture's size, stands for a whole rectangle of the picture of the label's proportions (a square on a disc; within a pixel each way), inside it and at least a pixel each way. | A label of one's own is never stretched, and never shows what is not in the picture. |
| INV-E7-06 | Library | A name the user gives a game is kept through saving, reading back and any rescan that keeps its file, on one line, trimmed and at most 80 characters; a blank one, or its own title, gives the game its title back. Only what is shown changes: the title, which identification and art look for and which keeps the game's place in its shelf, stays. | A game renamed keeps its name after a restart and a rescan, and its art and launches are not affected. |
| INV-E7-07 | Library | A name the user gives a console is kept through saving, reading back and rescans, as a game's name is (one line, trimmed, at most 80 characters); a blank one, or its own name, gives it its own back; it goes with its platform. | A console renamed keeps its name after a restart; removing the console forgets it. |
| INV-E7-08 | Shelves | The consoles show in the order the user put them in, on the consoles screen and after a restart: those put somewhere first, in that order, then the others in catalog order; putting some in another order later leaves those left out after them, in their order; removing a console leaves the others in their order. The console shown first is still the one remembered, wherever it now is. | Consoles ordered once stay so; a console added later does not upset them. |
| INV-E7-09 | Carousel | The ring putting the consoles in order has no end: n steps either way come back to the same console. Whatever is pressed, and when, its order holds every console exactly once, and each console stands where that order has it; let go (B), a console held leaves the order exactly as before; put down (A), the order is the one shown, kept by the plugin, or as before and told when it cannot be kept. Closed, the consoles screen is in the order kept. | Putting the consoles in order never loses or doubles one, and a change of mind always gives the old order back. |
| INV-E7-10 | Carousel | By touch, nothing launches a game: whatever a finger does (taps, long presses, drags and swipes anywhere, on any screen), only A does. A press that moves past the slop is never a tap, one held still is a long press at most once, and neither a second finger nor a touch the system takes back (its back gesture, a pinch) counts. | A finger never starts a game by mistake. |
| INV-E7-11 | Carousel | A drag on the consoles screen, or one that starts beside the game in the middle, moves one console or game, where there is one that way, the way the finger first got 80 pixels (of the 1280-wide screen) sideways from where it came down, whatever its length, its speed, its turns or a pause before it; a drag that never gets that far moves none. | One swipe, one game: never two, never a run. |
| INV-E8-01 | Carousel | Whatever the app's rest (drawn 30 times a second, or still), the first press, push of a stick past 0.3 of its travel, touch or return to the app wakes it at once, and that press, push or touch acts as it always does: none is lost. | Resting never stands between the user and the app. |
| INV-E8-02 | Settings | The edges are smoothed 4× unless the user chooses less (2× or none) in the settings; their choice is kept across restarts, settings stored before it existed read as 4×, and nothing else lowers it. | A visible compromise is only ever the user's choice. |
| INV-E9-01 | Search | A game of the shelf is found exactly when each word typed is the start of another word of its title, in any order (accents, case, signs and the word "the" left out); the games found keep the shelf's order. | The search never hides a game it should find, nor shows one it should not. |
| INV-E9-02 | Search | A key of the ribbon is lit exactly when typing it still finds a game (a space, when a key typed after it does). Once keys are typed, a lit key brings the carousel to the first of the games it finds; with nothing typed, to its letter's first game, or the next letter's. | No key leads to an empty carousel, and none that leads somewhere is dimmed. |
| INV-E9-03 | Carousel | Whatever is pressed on the games screen, the ribbon open or not, what is found kept or not, the pill names the game in the middle, A launches it, and B out of the ribbon (without keeping what it found) brings back the game shown when it was opened over the whole shelf. | The search never starts another game than the one shown, and never loses the user's place. |
| INV-E10-01 | Consoles | Every console folder has a manifest with no problem (its version a lower-case model code, hyphens between its words), whose platform has a profile (which gives its games' medium); each platform has exactly one default version; a new model of it has each of its moving parts at rest; its steps move only the moving parts its model declares and carry the fingerprint of the model as it is (its dimensions and its moving parts' values), and steps moving any other part are refused when read. | A console added in its own folder shows and launches, or a test says what is missing; steps tuned on another model, or on an older one, never play. |
| INV-E10-02 | Models | Every console folder's model, built from any dimensions its shape's rules accept, is closed part by part (but its single-face parts), every face turned outwards, each part placed by the shape (no node of it placed but a moving part's pivot); each moving part moves part of the console (a light lights it), a button pressed into it; each opening (a spring flap is one) moves a part; at rest each part an opening moves lies within the bounds of the rest of the console, and any other moving part (a button, a knob, a switch) stands out of them by 7 mm at most (the most a real console's buttons do); moving as the placeholder moves it (its rebound included), the others as the placeholder holds them then, and each part only a console's own steps move from rest to fully moved, no moving part passes through the rest of it; fully moved, a part pressed or slid without turning (a button, a switch) keeps its outermost point outside every part of the console it was outside of at rest, so that a pressed button still shows; all openings open at once, the part whose opening moves the seat (the one carrying the medium) still holds it, and no other moving part meets a box the size of the medium coming down its way in, from the seat to as far as the placeholder lifts it; its logos, the images of its folder, lie on a face of it, facing out, not mirrored, nothing that moves with them over them. Impossible dimensions are refused with the rules they break and build nothing. | INV-E5-07 for every console, without a test written per console. |
| INV-E10-03 | Launch | A console without steps of its own plays the placeholder made from its moving parts' roles: presented as the console says (by default its way in towards the camera), from rest, its buttons that are pressed and let go (eject, open) are pressed as it comes forward and let go by the time an opening is open; its openings open before the games screen and stay open until the medium, come down its way in from its own length and more, is seated, then close before the black, its power, lights and spinning parts on once they are, a momentary power button pressed then and let go before the black; its spring flaps are open once the medium is out of the row over the seat, before it comes down onto them, and stay open; the parts only its own steps move (a reset button, a door aside) stay at rest; the whole screen is black at most 2.4 s after the launch. | Every console launches a game as soon as its model exists, as fast as the PS2. |
| INV-E10-04 | Consoles | A console's scene is loaded only when the console, or its launch animation, is first asked for: only the consoles of the library are loaded. Likewise only the media of the library's games are loaded; the row's models of a shelf's media, and their launch animations, are made as the shelf is selected, never on A, and freed once the library has no game of that medium. | More consoles or media cost nothing to a library without them. |
| INV-E10-05 | Media | Every game gets a medium its platform's profile declares, whatever its regions: a platform of one medium gives it to all its games; a game sold in a PAL land takes the default, otherwise one sold in the Americas the NTSC-U medium, otherwise one sold in East Asia the NTSC-J medium, each falling back to the default when the platform declares none; a game of no known region takes the default; the order of a game's regions changes nothing. | INV-E10-06 | Art | A game only ever gets scans from its own platform's sources (a title naming games of two platforms never mixes their scans), each read for the medium its regions give it, by the kind of scan its platform's profile declares: a disc's label is its whole face on a square; a cartridge's label never comes from a scan of another shape than the front it is cut by: it is cut by the first front (its own medium's, then the profile's others in order) whose proportion the scan's is within 6 % of (6 % of the front's), where that front's label crop puts it (fractions of the cartridge, inside it), in whole pixels inside the scan, within a pixel of the crop, at its own proportions; a scan of no front's shape gives no label and the next scan is tried. Every medium a cartridge platform declares has its front, and the fronts of one platform are further apart than the tolerance; each cartridge medium's label face has the proportions of the labels cut for it within 2 %, and every front is of its model's proportion within 2 % (but the ones named whose scans have another shape, the PAL SNES's) and cuts the label where the model's label lies on its front, each corner within 0.005 of the cartridge, and any image shows on a label covering its face, centred, never stretched. Every shipped art extract belongs to a platform whose profile declares its kind, cartridge fronts for a cartridge platform, a disc otherwise; a label crop off its cartridge, a front of no proportion, or a serial source whose form of serial is no pattern, is refused when the profiles are read. | Every console's labels are its own games', framed as on the real cartridges, even from a scan of a regional cartridge or a scan list with photos taken at an angle, by rules given as data. |
| INV-E10-07 | Media | Every medium folder has a manifest with no problem (its kind, its scene, its triangle budget), its medium one a platform's games come in, unless listed for the consoles' variants (whose scans' fronts may be declared already), and every platform declaring it, as its games' medium or as the front of its scans, of its kind; its model has a `Label` built from its shape and is drawn within its budget; its own dimensions are accepted, and built from any dimensions its shape's rules accept, its parts together are closed, every face turned outwards, its label on the medium, within the bounds of its other parts, its image upright on it (each point of a cartridge's label at the place of the image it has over the label's bounds, of a disc's over the disc's square); at its real size it fills exactly the real medium's width, height and thickness, as sourced or measured, within 0.7 mm (its reliefs); impossible dimensions are refused with the rules they break and build nothing; the title and the platform's name are drawn centred on its label's face; every medium a console's platform declares comes down that console's way in at its real size (seated at it, whatever its size in the row, and lifted from its real length) clear of every opening but the one carrying it, as INV-E10-02 checks for one, and every vertex of it, half a millimetre in, through none of the console's parts that never move but those it lies in, drawn solid; a medium known by its colour keeps it (the PlayStation's disc black, every other disc silver underneath, the Game Boy Color's cartridge the Game Boy's grey one, the Nintendo 64's contacts gold). | INV-E11-01 | Library | A file whose content (a disc's serial, a cartridge's print) names one game is given that game, whatever its name says: that very version when a single one has the content, or is written like its name, or alone has its name's country; otherwise the game's title, with the countries and serials all its versions share. | INV-E11-02 | Art | Several games a title finds alike are told apart by putting back, one at a time, its punctuation (`: ` and ` - ` alike), its accents, then its exact text, keeping those whose name is still the title; a title that names none of them or several still once the ladder is climbed gives no image, whichever of them has scans. | A title close to two games' names shows the one it really names; one that could be either never shows another game's label. |
| INV-E11-03 | Files | Reading a game file never changes it (the `ByteSource` port has no way to write), never asks for bytes outside it, and never throws: whatever the bytes, `FileReading.facts` answers a serial, a print or nothing (`Silent`), only the port failing to read being a failure (`ReadFailure`); whatever a CHD claims (its hunks, their lengths, its map, its metadata, hunks repeating others in chains), no read asks more than a hunk, the map's 9 bytes a hunk or a few KB of metadata. The plugin opens a game file read-only, through its documents provider, and closes it once read; a file it cannot open or read is identified by its name and read again at the next scan, never remembered as telling nothing; a document that is not a file (a pipe, of no size) tells nothing, and is remembered so. | The user's files are never touched, and a damaged, truncated or unknown file costs the library nothing. |
| INV-E11-04 | Art | The app never asks ScreenScraper which game a file is: it only downloads images (`mediaJeu.php`) that its shipped texture table (`app/data/screenscraper`) lists for the game's release, under its reference name, with the system its platform's profile names; a release the table lacks costs no request. | INV-E11-05 | Art | Every ScreenScraper request goes through one gate: one at a time with the app's key alone, the member's threads and per-minute allowance with an account (read by `ssuserInfos.php` at the first request of each day, itself a request; a refused member, by a 403, the user-login text or a level of 0, leaves the key alone from then on; any other answer says nothing of the member: it counts for the state as a request's would, and the day stays unchecked); a 429 makes the next request wait 10 s from its arrival (the requests already under way then change nothing, whatever they answer), and a 429 to a request sent after that closes ScreenScraper for the run, as do 401, 423, a timeout, a server out of reach while the network is up, or an answer that is neither an image nor a text the app knows; 430 and 431 close it until the next day, kept across restarts; a refused key (403, 426, or a login error on an image) turns it off for good, kept across restarts for that key (as a hash: a build with another key starts open, a closure until a day holding still); an answer that comes once it is closed never makes the closure lighter.
